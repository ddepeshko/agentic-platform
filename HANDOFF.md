## 3. Поточний стан

- **Модуль:** 0 (Старт і вимоги), тиждень 1.
- **Зроблено в чаті:** узгоджено програму й стек, видано план тижня 1. Користувач ще **не відзвітував** про виконання дня 1.
- **Наступний крок користувача (день 1):**
  1. Створити репозиторій, ініціалізувати TypeScript-проєкт (Node LTS, `tsc` або `tsx`, ESLint).
  2. Структура папок: `src/core`, `src/platform`, `src/domain`, `evals/`.
  3. Отримати API-ключ, покласти в `.env`, додати `.env` у `.gitignore`.
  4. Зробити один виклик моделі з коду, що друкує відповідь.
- **План тижня 1:** день 2: описати 3 цільові агенти (що роблять, які дані читають, які дії виконують; один агент із дією, що змінює стан). День 3: зібрати `REQUIREMENTS.md` (користувачі, ролі, чого платформа не робить). Дні 4–5: довести документ і дати на рев'ю.

## 4. Правила менторства

1. **Спробуй сам, потім питай.** Якщо користувач застряг, давай підказку або навідне питання, а не готове рішення. Готовий код пиши лише тоді, коли користувач прямо просить або вже зробив кілька спроб.
2. **Кожен модуль закінчується** працюючим кодом, виконаним чекпоінтом і короткою нотаткою «що я вирішив і чому».
3. **Рев'ю коду:** що працює, де архітектурні ризики, які питання задали б на співбесіді.
4. **Не вигадуй стан.** Дивись у репозиторій, `PROGRESS.md` і `git log`, а не покладайся на припущення про попередні сесії.
5. **Ключі й секрети:** ніколи не виводь у відповідях, не коміть, не пиши в логи. Лише `.env`.
6. Відповідай стисло, без води, українською.
7. Веди в репозиторії `PROGRESS.md`: модуль, дата, рішення, відкриті питання. Оновлюй наприкінці кожної сесії.

> Порада: перенеси розділ 4 у `CLAUDE.md` у корені репозиторію, щоб ці правила діяли в кожній сесії автоматично.

## 5. Фінальний результат

- GitHub-репозиторій платформи з чіткою архітектурою.
- Реєстр агентів, тулів і MCP-серверів: новий агент додається конфігом, а не переписуванням коду.
- Модель прав: хто (користувач, агент) може викликати який тул, з якими обмеженнями й approvals.
- MCP gateway з політиками, лімітами й аудит-логом.
- Observability: трейси, вартість, латентність, replay.
- Evals із регресіями в CI.
- Три різні агенти, додані без змін у ядрі, та архітектурна документація.

**Фінальний «екзамен»:** користувач додає четвертого агента з новим тулом і новими правами, а `git diff` чіпає лише конфіг і домен, не ядро.

## 7. Деталі модулів

### Модуль 0. Старт і вимоги

Визначити, кого обслуговує платформа, описати 3 цільові агенти, створити репозиторій зі структурою `src/core`, `src/platform`, `src/domain`, `evals/`. Чекпоінт: `REQUIREMENTS.md` на 1–2 сторінки (користувачі, ролі, три агенти, що платформа не робить).

### Модуль 1. Agent loop з нуля

Messages, system prompt, tool calling через API. Цикл Think → Act → Observe, умови зупинки, ліміт кроків. Structured outputs і валідація через Zod. Керування контекстом. Завдання: агент в одному TS-файлі з 2–3 тулами, лімітом ітерацій і логуванням кожного кроку. Чекпоінт: зупиняється сам і за лімітом, помилка тула не валить цикл, зрозуміло, що потрапляє в контекст на кожному кроці.

### Модуль 2. Tool layer

Тул як контракт: ім'я, опис, схема входу й виходу, поведінка при помилках. Zod/JSON Schema, таймаути, retry, ідемпотентність, класифікація помилок. read-only і write-тули. Версіонування тулів. Завдання: `ToolRegistry` з метаданими `readOnly`, `riskLevel`, `owner`. Чекпоінт: новий тул додається одним файлом без змін у циклі агента.

### Модуль 3. MCP: сервер і клієнт

Архітектура MCP (сервер, клієнт, tools, resources, prompts), транспорти stdio і streamable HTTP, MCP Inspector. Різниця між «тул у коді» і «тул через MCP». Завдання: власний MCP-сервер з 2–3 тулами для доменного сервісу і MCP-клієнт у ядрі, що підключає його до реєстру тулів. Чекпоінт: агент викликає і локальний тул, і MCP-тул через один інтерфейс.

### Модуль 4. Ядро платформи

Агент, тул і MCP-сервер як **дані**, а не код. Таблиці: `agents`, `agent_versions`, `tools`, `mcp_servers`, `agent_tool_bindings`, `runs`, `run_steps` (+ закласти `users`, `roles`). Конфіг агента: модель, system prompt, дозволені тули, ліміти, версія. Runtime, що за `agentId` збирає агента з БД і запускає. Версіонування й rollback. Міграції та seed. Завдання: Postgres-схема, API `POST /agents`, `POST /agents/:id/run`, перші два агенти як записи в БД. Чекпоінт: новий агент створюється запитом до API без редагування коду, кожен run зберігається з кроками.

### Модуль 5. Права, ідентичність, approvals

Ідентичність: користувач, агент, сервісний акаунт; від чийого імені викликається тул. Моделі доступу: RBAC, ABAC, політики на кшталт «агент A може викликати тул X лише з параметром Y». Least privilege. Human-in-the-loop: `always_ask`, `ask_once`, `allow`. Секрети й креденшіали: зберігати окремо, підставляти на рівні платформи, **не показувати моделі**, ротація. OAuth для віддалених MCP-серверів (розділ про авторизацію в специфікації MCP), токени користувача проти токенів платформи, confused deputy. Завдання: policy engine `decide(identity, agent, tool, args) → allow | deny | ask`, таблиці ролей і біндингів, approval-флоу з очікуванням рішення. Чекпоінт: агент без дозволу на тул отримує `deny`, у відповіді моделі немає секретів; write-тул без approval не виконується; усі рішення політики пишуться в аудит.

### Модуль 6. MCP gateway

Весь трафік до MCP-серверів іде через gateway: discovery, виклик, фільтрація списку тулів. Rate limits, квоти, бюджети на агента й користувача. Аудит-лог: хто, коли, який тул, з якими параметрами, яке рішення. Редакція чутливих даних у логах. Завдання: винести перевірки з модуля 5 у gateway-шар. Чекпоінт: заборонений тул не лише блокується, а й **не з'являється** у списку тулів агента.

### Модуль 7. Observability

Трейс запуску: LLM-виклики, тули, MCP, рішення політик. Вартість і токени на запуск, агента, користувача. Латентність по кроках. OpenTelemetry і Langfuse. Replay помилкового run за збереженими кроками. Алерти: стрибок вартості, зростання помилок тулів. Завдання: інструментувати runtime й gateway, підключити Langfuse (або OTel + Phoenix), дашборд вартості й помилок. Чекпоінт: за ID запуску за хвилину знаходиш, який тул упав, скільки коштував run і що бачила модель.

### Модуль 8. Evals

Датасети кейсів, критерії успіху, детерміновані перевірки та LLM-as-judge. Evals траєкторій: чи викликав агент потрібні тули у правильному порядку. Окремі кейси на **права**: агент не повинен мати змоги виконати заборонене. Регресії в CI, порівняння версій промптів і моделей. Завдання: 20–30 кейсів на агента, скрипт прогону, запуск у CI. Чекпоінт: зміна промпта запускає eval, видно різницю в метриках до мерджа.

### Модуль 9. Безпека й guardrails

Prompt injection через дані з тулів і документів. Tool poisoning: шкідливі описи тулів у зовнішніх MCP-серверах. Витік даних між тулами (приватні дані + недовірений вміст + зовнішні дії). Валідація входу й виходу тулів, allowlist доменів, sandbox для виконання коду. Довіра до MCP-серверів: реєстр схвалених, пінінг версій. Завдання: шар перевірок на вхід/вихід тулів, список схвалених MCP-серверів, red-team кейси в evals. Чекпоінт: ін'єкція в документі не призводить до виклику write-тула без approval.

### Модуль 10. Знання й пам'ять як сервіс

RAG з нуля: чанкінг, ембеддинги, pgvector, пошук, оцінка якості. Відмінність пам'яті, контексту й бази знань. Права на знання: агент бачить лише документи, до яких має доступ користувач. Завдання: RAG-тул і memory-тул у реєстрі, обидва з перевіркою доступу на рівні документа. Чекпоінт: два користувачі з різними правами отримують різні відповіді на однакове питання.

### Модуль 11. Production

Докеризація, конфігурація середовищ, міграції. Черги й довгі процеси: retry, ідемпотентність, durable execution (Inngest або Temporal як референс). Model gateway: кілька провайдерів, fallback, ліміти. Бюджети й кіл-світч для агента, що «біжить» не туди. Streaming статусів виконання для UI. Завдання: задеплоїти платформу, додати чергу для довгих запусків і fallback моделі. Чекпоінт: падіння провайдера не зупиняє платформу, перевищення бюджету зупиняє run.

### Модуль 12. Адмін-UI і фінальний проєкт

Адмін-інтерфейс: список агентів, створення агента, вибір тулів і MCP-серверів, налаштування прав, перегляд запусків і трейсів. Три агенти з модуля 0 створені через UI. Архітектурна документація: схема компонентів, модель даних, модель прав, відомі ризики, компроміси. Demo і розбір: користувач пояснює архітектуру, ментор грає роль інтерв'юера. Екзамен: четвертий агент з новим тулом і правами без змін у ядрі.
